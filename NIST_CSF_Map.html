// WHAT IS NIST CYBERSECURITY FRAMEWORK 2.0?
The NIST Cybersecurity Framework (CSF) 2.0 is a set of voluntary guidelines published by the National Institute of Standards and Technology to help organizations manage cybersecurity risk. Released in 2024, version 2.0 added a critical new function: GOVERN.

Where MITRE ATT&CK describes how attackers operate, NIST CSF 2.0 describes how defenders should be organized. The framework asks: "At each stage of a cyber event, what should your organization be doing?"

The SolarWinds breach is a textbook case study for NIST CSF 2.0 because it exposed failures in every single function — from governance to recovery.

// CSF 2.0 vs CSF 1.1 — WHAT CHANGED
CSF 1.1 (2018) — 5 Functions
Identify → Protect → Detect → Respond → Recover
Security treated as a technical problem
CSF 2.0 (2024) — 6 Functions
Govern → Identify → Protect → Detect → Respond → Recover
Security is now a business governance problem
💡 Key insight: NIST CSF 2.0 added GOVERN because the SolarWinds breach (and others like it) showed that technical controls alone aren't enough. When leadership doesn't treat security as a core business function, no amount of firewalls or patches can compensate. The board must own cybersecurity risk.
// THE SOLARWINDS SUPPLY CHAIN ATTACK — STEP BY STEP
The SolarWinds attack (2020) is one of the most sophisticated cyber espionage operations ever conducted against the United States. Unlike Colonial Pipeline, where attackers entered through a stolen password, SolarWinds attackers compromised the software itself — turning a trusted IT management tool into a weapon delivered to 18,000+ customers including the US Treasury, DOJ, Pentagon, and Fortune 500 companies.
1
Infiltrate the SolarWinds Build Environment (Oct 2019)
Russian SVR hackers (APT29 / Cozy Bear) gained access to SolarWinds' internal software development environment at least 14 months before discovery. They studied the build pipeline, learned how software was compiled and signed, and tested their malicious code as a trial run without deploying it.
GOVERN failure — No supply chain security policyPROTECT failure — Build system accessibleT1195.002 — Supply Chain Compromise
2
Inject SUNSPOT Malware into the Build System (Feb 2020)
Attackers deployed a tool called SUNSPOT into SolarWinds' CI/CD (continuous integration/continuous delivery) pipeline. SUNSPOT monitored the build process and, when the Orion software was being compiled, it replaced a legitimate source file with a malicious version containing SUNBURST backdoor code — all while hiding its tracks.
PROTECT failure — No build integrity verificationPROTECT failure — Code signing did not catch thisDwell time: 14+ months undetected
3
SolarWinds Orion Update Ships with SUNBURST (Mar–Jun 2020)
SolarWinds released software updates for Orion (versions 2019.4 through 2020.2.1) that contained the SUNBURST backdoor. Because the updates were digitally signed with SolarWinds' legitimate certificate, every security tool trusted them. Approximately 18,000 organizations installed the poisoned update.
IDENTIFY failure — Organizations didn't track software supply chain riskPROTECT failure — Trusted signature = no inspection18,000 organizations affected
4
SUNBURST Establishes Dormant Backdoor (Mar–May 2020)
After installation, SUNBURST waited 12–14 days before activating to avoid sandbox detection. It then checked whether it was in a security researcher's environment. If not, it began "beaconing" — sending periodic encrypted check-in calls to a command-and-control server disguised as legitimate Orion network traffic. Domain: avsvmcloud[.]com.
DETECT failure — C2 traffic blended with legitimate Orion trafficDETECT failure — 12-day delay bypassed most sandboxes
5
Selective Exploitation of High-Value Targets (May–Dec 2020)
From 18,000 infected organizations, attackers selectively activated full backdoor access in only ~100 high-value targets — US government agencies, defense contractors, and technology companies. They stole emails, security tools, and classified information. The targeted organizations had no idea anything was wrong — Orion appeared to be running normally.
DETECT failure — No anomaly detection on outbound dataVictims: Treasury, DOJ, State Dept, DHS, FireEye
6
FireEye Discovers the Breach (Dec 8, 2020)
Cybersecurity firm FireEye noticed a suspicious second device registration on their own network attempting MFA enrollment — an attacker trying to add their phone to an employee's account. Investigating, FireEye discovered SUNBURST in their Orion installation. They immediately notified SolarWinds, Microsoft, and the US government.
Discovery: external firm, not SolarWinds or victimsDETECT failure — No internal detection for 9 months
7
Emergency Response & Recovery (Dec 2020 – months)
CISA issued Emergency Directive 21-01 — the strongest directive ever issued — ordering all federal agencies to immediately disconnect Orion. SolarWinds issued patches. Microsoft seized the C2 domain. But recovery was not simply "patch and restart" — affected organizations had to assume every credential, every secret, every token in systems touched by Orion was compromised and rebuild from scratch.
RESPOND failure — No playbook for supply chain compromiseRECOVER failure — Full rebuild required, not a patchCISA ED 21-01 — mandatory federal disconnect
// NIST CSF 2.0 FUNCTION ANALYSIS — SOLARWINDS
For each of the 6 NIST CSF 2.0 functions, review: what subcategories apply, how SolarWinds failed that function, and what controls would have helped. Use these as your reference for the Student Worksheet.
GV — GOVERN
Organizational Cybersecurity Strategy & Oversight
FAILED
What this function covers
Leadership establishes cybersecurity roles, policies, and accountability. The board and C-suite own cyber risk as a business risk. Policies govern how software is developed, reviewed, and released.
How SolarWinds failed GOVERN
SolarWinds had no formal policy requiring security review of its build pipeline. The CEO later said security teams were stretched thin. There was no executive accountability for software supply chain risk. A 2019 internal email even noted that a SolarWinds server password ("solarwinds123") was exposed on GitHub for months.
Key GOVERN subcategories that were absent
GV.PO-01 — Cybersecurity policy established and maintained
GV.RM-06 — Cybersecurity risk included in enterprise risk management
GV.SC-06 — Cybersecurity requirements for suppliers and third parties
What control would have helped
A formal Software Development Lifecycle (SDLC) security policy requiring independent security review of the build pipeline, plus board-level reporting on supply chain risk.
ID — IDENTIFY
Asset Management & Supply Chain Risk
FAILED
What this function covers
Know every asset in your environment, including third-party software. Understand which vendors have access to your network and treat software updates from vendors as potential attack vectors — not automatic trust.
How SolarWinds victims failed IDENTIFY
Most of the 18,000 infected organizations had no Software Bill of Materials (SBOM) — they didn't know which systems ran Orion, what version, or what access it had. They also didn't track that Orion required admin-level access to the network, making it an extremely high-risk dependency.
Key IDENTIFY subcategories that were absent
ID.AM-02 — Software and services inventoried
ID.SC-02 — Suppliers assessed for cybersecurity practices
ID.SC-04 — Suppliers monitored to confirm they meet commitments
What control would have helped
Maintaining a Software Bill of Materials (SBOM) for all third-party software, and conducting annual vendor security assessments — specifically evaluating whether SolarWinds' build process had integrity controls.
PR — PROTECT
Build Pipeline Integrity & Access Controls
CRITICAL FAILURE
What this function covers
Implement safeguards: access controls, software integrity verification, network segmentation, encryption, and awareness training. The goal is to limit the impact when (not if) something goes wrong.
How SolarWinds failed PROTECT
The build server (where code is compiled) was not isolated from the rest of the network. Attackers were able to reach it and inject SUNSPOT without triggering alerts. There was no build integrity verification — no mechanism to detect that a source file had been swapped during compilation. The malicious code was signed with SolarWinds' legitimate certificate, meaning digital signing alone was not a sufficient control.
Key PROTECT subcategories that were absent
PR.AC-03 — Remote access managed
PR.DS-01 — Data at rest protected
PR.IP-02 — Software development follows security practices (SSDLC)
PR.IP-12 — Vulnerabilities identified and remediated
What control would have helped
Reproducible builds with cryptographic hash verification of every compiled binary before signing — so any modification to source code would produce a different hash and fail the check. Also: isolating the build environment on a separate air-gapped or strictly firewalled network.
DE — DETECT
Anomaly Detection & Continuous Monitoring
FAILED — 9–14 Months
What this function covers
Continuously monitor systems and network traffic for anomalies. Establish baselines for normal behavior so deviations — like unusual outbound connections or unexpected admin tool activity — trigger alerts.
How SolarWinds victims failed DETECT
SUNBURST was designed to blend in: it used legitimate Orion network protocols, randomized beacon intervals (12–14 hour delays), and only activated in non-sandbox environments. Without behavioral baselines, security teams couldn't distinguish malicious Orion beaconing from normal Orion traffic. The SIEM logs existed but nobody was analyzing them for this pattern.
Key DETECT subcategories that were absent
DE.AE-01 — Network activity baseline established
DE.AE-03 — Event data aggregated and correlated
DE.CM-01 — Network monitored to detect potential events
DE.CM-07 — Monitoring for unauthorized personnel, connections, devices
What control would have helped
DNS monitoring with anomaly detection — SUNBURST used DNS queries to resolve its C2 domain. Any tool that baselines DNS query patterns would have flagged the unusual subdomain patterns of avsvmcloud[.]com. UEBA (User and Entity Behavior Analytics) would also have flagged the anomalous beacon intervals.
RS — RESPOND
Incident Response & Communication
UNPREPARED
What this function covers
Have a plan before an incident happens. Know who to call, how to contain a breach, how to communicate with stakeholders, and how to analyze what happened. Supply chain incidents require coordination across hundreds of organizations simultaneously.
How organizations failed RESPOND
No organization had an incident response playbook for "our trusted network management software is a backdoor." When CISA issued Emergency Directive 21-01, many agencies did not know which systems ran Orion or what "isolate Orion systems" even meant in practice. The response had to be improvised across 18,000 organizations in real time.
Key RESPOND subcategories that were absent
RS.RP-01 — Response plan executed during or after incident
RS.CO-02 — Incidents reported per established criteria
RS.AN-01 — Notifications from detection systems investigated
RS.MI-01 — Incidents contained
What control would have helped
A pre-written supply chain compromise playbook with pre-authorized steps for isolating affected software, pre-identified escalation contacts at CISA, and pre-staged clean network segments for failover.
RC — RECOVER
Recovery Planning & Resilience
MONTHS-LONG
What this function covers
Restore normal operations after a cybersecurity incident. This is more than rebooting systems — it means confirming the attacker is gone, systems are clean, and the root vulnerability is fixed so re-compromise doesn't happen immediately.
How organizations failed RECOVER
Because Orion had admin-level access to network infrastructure, recovery wasn't "patch Orion." It meant treating every credential, token, and certificate in the environment as compromised. Some agencies took months to complete recovery. Treasury and DOJ reportedly had to rebuild entire email systems. Determining whether attackers had persisted through mechanisms beyond SUNBURST took specialized forensic analysis most organizations couldn't perform internally.
Key RECOVER subcategories that were absent
RC.RP-01 — Recovery plan executed during or after incident
RC.IM-01 — Recovery plan incorporates lessons learned
RC.CO-03 — Recovery activities communicated to stakeholders
What control would have helped
Pre-tested recovery procedures including credential rotation playbooks, clean image backups of critical systems stored offline, and a tiered asset classification system so high-risk assets (those with admin-level software like Orion) could be prioritized and rebuilt first.
